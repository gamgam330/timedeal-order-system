# [타임딜 #05] 품절 한 마디에 DB를 세 번 — Redis 재고 카운터 (DECR vs Lua)

> **이번 글 요약**
> 1. 재고 100개가 다 팔린 뒤에도, "품절" 안내만 받으면 되는 주문까지 **전부 DB를 거쳐 갔다.** 품절 주문 하나마다 DB에서 SQL이 3개씩(UPDATE, SELECT, ROLLBACK) 실행됐고, 주문이 초당 3,000건 몰리자 품절 응답이 **0.6초**, 상관없는 상품 조회도 0.6초가 됐다.
> 2. 재고 숫자를 Redis에도 적어 두고 주문이 오면 거기서 먼저 줄이게 하자, 품절 주문은 DB에 한 번도 가지 않았다. 품절 응답은 0.6초에서 **0.0015초**(1.5ms)가 됐다.
> 3. 그런데 결제가 실패해도 Redis 숫자는 그대로라서, **다시 팔 수 있는 재고 19개가 테스트 3분 내내 안 팔렸다.** 실패한 만큼 Redis 숫자도 되돌리고, "남은 수량 확인"과 "줄이기"를 Lua 스크립트 하나로 묶어 그 사이에 다른 주문이 끼어들지 못하게 고쳤다.
>
> | 방식 | 품절 응답 (초당 3,000건) | 다른 상품 조회 | 결제 20% 실패 시 판매 (재고 100개) |
> |---|---|---|---|
> | 원자적 UPDATE만 (지난 글 결론) | **0.57~0.64초** ❌ | **0.56~0.63초** ❌ | 100개 ✅ |
> | Redis DECR (처음 버전) | 0.94ms ✅ | 4.02ms ✅ | **81개** ❌ |
> | Redis Lua + 되돌리기 (최종) | 1.49ms ✅ | 5.46ms ✅ | 100개 ✅ |

## 먼저 알아 둘 것: 은행으로 보는 서버

지난 글과 같은 은행 비유를 이어서 쓴다.

| 서버 | 은행 | 이 프로젝트에서 |
|---|---|---|
| 요청 | 손님 | 주문, 상품 조회 |
| Tomcat 스레드 | 직원 | 요청 하나를 맡아 끝까지 처리한다. 200명 |
| DB 커넥션 | 창구 | 장부(DB)를 보려면 창구에 앉아야 한다. 10개 |
| 상품 재고 행 | 장부 한 페이지 | `product` 테이블의 1번 상품 행 |
| 행 락 | 장부 사용권 | 이 페이지는 한 번에 한 직원만 고친다 |
| 커밋 / 롤백 | 도장 찍기 / 고친 것 지우기 | 도장을 찍어야 고친 내용이 확정된다. 롤백은 고친 걸 없던 일로 한다 |
| **Redis** | **입구 안내판** | 이번 글에서 새로 등장. 남은 수량을 적어 두는 곳 |

> **용어**
> - **p95**: 응답 100개를 빠른 순으로 세웠을 때 95번째. "대부분의 손님이 이 시간 안에 끝났다"는 뜻이다.
> - **RPS / TPS**: K6가 1초에 **보내기로 한** 요청 수(목표) / 서버가 1초에 **실제로 처리해 낸** 요청 수. 본문에서는 TPS를 "처리량"이라고 쓴다.
> - **ms**: 1초의 1,000분의 1. 0.6초 = 600ms.

## 지난 글에서 남은 문제

[지난 글(#04)](https://90000e.tistory.com/23)에서 Redis 분산 락을 붙여 봤다가, 재고 차감은 결국 원자적 UPDATE로 돌아왔다.

```sql
UPDATE product SET stock = stock - 1 WHERE id = 1 AND stock >= 1
```

정확하게 100개만 팔린다. 그런데 테스트 결과를 보다가 하나가 걸렸다. **재고가 0이 된 뒤에 온 손님도 이 UPDATE를 똑같이 실행한다.** "바뀐 행이 0개"라는 답을 받고 나서야 "품절"을 듣는다.

코드를 따라가 보니 품절 손님 한 명이 DB에서 하는 일은 세 가지였다.

| 순서 | DB에서 하는 일 | 이유 |
|---|---|---|
| 1 | `UPDATE ... WHERE stock >= 1` → 0행 | 재고 차감 시도 |
| 2 | `SELECT` 상품 | 품절 메시지에 넣을 남은 재고 조회 |
| 3 | `ROLLBACK` | 품절 예외가 나서 트랜잭션을 되돌림 |

은행으로 치면, 물건이 다 팔렸는데도 손님마다 직원이 붙어서 창구에 앉고 장부를 펴 본 뒤에 "다 팔렸네요"라고 말하는 셈이다. 재고 100개에 10만 명이 몰리면 99,900명이 이 과정을 거친다.

그래서 이번에는 **품절 손님을 창구까지 보내지 않는 방법**을 찾아보기로 했다.

## 품절 손님이 DB에 주는 부담 측정

먼저 지금 상태를 쟀다. 재고 100개 상품에 주문을 계속 보내면서, 상관없는 상품 조회도 초당 50건씩 함께 보냈다. 품절 손님이 다른 손님까지 느리게 만드는지 보려는 것이다.

이번에는 응답 시간과 함께 **DB가 실제로 실행한 SQL 수**도 셌다. MySQL은 서버를 켠 뒤 실행한 UPDATE, SELECT 수를 계속 세고 있어서(`SHOW GLOBAL STATUS`), 테스트 전후 값을 빼면 테스트 동안 몇 번 실행됐는지 나온다.

### 초당 900건까지의 결과

| 주문 RPS | 판매 | 품절 | 품절 응답 p95 | 다른 상품 조회 p95 |
|---|---|---|---|---|
| 300 → 600 → 900 (3분) | 100 | 101,147 | 2.42ms | 3.51ms |

솔직히 느려질 줄 알았는데 **멀쩡했다.** 응답 시간만 봤다면 "문제없음"으로 끝냈을 것 같다.

그런데 DB가 실행한 SQL 수를 보니 이야기가 달랐다.

| UPDATE | SELECT | ROLLBACK |
|---|---|---|
| 101,347 | 110,349 | 101,147 |

UPDATE 101,347번 중 재고를 줄인 건 100번, 주문 상태를 바꾼 건 100번이다. 나머지 101,147번은 전부 품절 손님이 실행한, 아무것도 바꾸지 못한 UPDATE였다. SELECT 110,349번도 품절 손님 101,147번에 다른 상품 조회 약 9,000번과 판매 쪽 200번을 더한 값과 거의 맞았다. **10만 번 넘게 "품절" 한 마디를 위해 장부를 폈다.** 아직 느리지 않을 뿐, DB는 그만큼 일하고 있었다.

### 초당 3,000건에서의 결과

그럼 더 몰리면 어떻게 될까 싶어서 1,500 → 3,000으로 올려 봤다. 같은 조건으로 두 번 쟀다.

| 회차 | 품절 응답 p95 | 다른 상품 조회 p95 | 보내지도 못한 요청 |
|---|---|---|---|
| 1 | **644ms** | **634ms** | 17,821 |
| 2 | **568ms** | **560ms** | 8,822 |

- "보내지도 못한 요청"은 응답이 늦어져서, K6가 손님 역할로 띄워 두는 가상 사용자(최대 1,500명)가 모두 응답을 기다리느라 보내지 못한 요청이다.
- 두 회차의 숫자 차이가 큰 건, 맥북 한 대에서 K6와 서버가 함께 돌아서 생긴 흔들림으로 봤다. 숫자보다 모양(둘 다 0.6초 근처로 느려짐)을 봤다.

품절 손님만 느려진 게 아니라 **상관없는 상품 조회까지 0.6초**가 됐다. 지난 글들에서 본 그 모양이다. 누군가 다 같이 쓰는 자리(창구)를 다 차지하고 있다는 뜻이다.

## 줄이 생긴 진짜 이유: 품절 손님끼리의 장부 사용권 대기

### 처음 내린 결론

구간을 나눠서 서버 쪽 수치를 봤다.

| 수치 | 1,500 구간 | 3,000 구간 |
|---|---|---|
| 서버가 처리한 주문 (초당) | 1,500 | **2,766** (목표 3,000) |
| 창구(커넥션) 한 번 쓰는 시간 | 0.8ms | **3.5ms** |
| 사용 중인 창구 | 평균 1.3개 | **10개 전부** |
| 창구를 기다리는 손님 | 0 | **최대 190명** |
| 일하는 직원(Tomcat 스레드) | 최대 2명 | **200명 전부** |

창구 10개가 다 차고 190명이 기다렸다. MySQL CPU는 약 60%였다(CPU 2개를 줬으니 최대 200%). 그래서 처음엔 **"DB는 여유 있는데 창구가 모자라다"** 고 정리했다.

### 결론을 뒤집은 수치

다시 보다가 이상한 점이 하나 있었다. 창구 한 번 쓰는 시간이 0.8ms에서 **3.5ms로 네 배 넘게** 늘었다. 하는 일(UPDATE, SELECT, ROLLBACK)은 똑같은데 왜 길어졌을까.

찾아보니 UPDATE는 재고가 0이어도 **1번 페이지의 사용권부터 받고(행 락), 그다음에** `stock >= 1`인지 확인한다. 그리고 MySQL 기본 설정인 REPEATABLE READ(#03에서 본 격리 수준)에서는 조건에 안 맞은 행이어도 트랜잭션이 끝날 때(ROLLBACK)까지 사용권을 놓지 않는다고 한다. READ COMMITTED로 바꾸면 조건을 확인한 직후에 놓는다는데, 측정 조건을 바꾸지 않으려고 기본값 그대로 뒀다. 그렇다면 품절 손님들끼리도 1번 장부 페이지 앞에 한 줄로 서 있었을 수 있다.

MySQL은 행 락을 기다린 횟수와 시간도 센다. 그것까지 넣어서 다시 쟀다.

| UPDATE 횟수 | 그중 장부 사용권을 기다린 횟수 | 기다린 시간 합계 |
|---|---|---|
| 238,770 | **141,897 (59%)** | **386초** (한 번에 평균 2.7ms) |

절반 넘게 기다리고 있었다. 정리하면 이랬다.

1. 품절 손님들이 1번 장부 페이지의 사용권을 하나씩 돌려 가며 기다린다.
2. 기다리는 동안에도 창구에 앉아 있으니 창구 한 번 쓰는 시간이 늘어난다 (0.8ms → 3.5ms).
3. 창구 하나는 1초(1,000ms)에 약 285명(1,000 ÷ 3.5)을 받는다. 창구가 10개니 초당 약 2,860명. 이게 이 구조로 받을 수 있는 최대치였고, 실제로 잰 2,766과 거의 맞았다.
4. 창구가 꽉 차니 상관없는 조회 손님도 창구를 못 잡는다.

**줄은 창구 앞에 섰지만, 줄이 생긴 이유는 장부 앞이었다.** 사용권을 기다리는 동안에는 CPU를 쓰지 않으니, CPU만 봤을 때 DB가 한가해 보였던 것이다.

> **정리**: 품절 요청이 DB를 거치는 부담은 처음엔 응답 시간이 아니라 DB가 실행한 SQL 수로만 보였다. 더 몰리자 품절 손님끼리 장부 사용권을 기다리느라 창구를 오래 붙잡았고, 그 줄에 상관없는 손님까지 같이 섰다.

## Redis 재고 카운터: 입구에서 돌려보내기

해결 방법은 단순했다. **남은 수량을 입구 안내판(Redis)에 적어 두고, 손님이 들어올 때 거기서 먼저 하나 줄인다.** 안내판이 "0"이면 직원이 창구에 앉지 않고, 입구에서 바로 "품절입니다"라고 돌려보낸다.

지난 글에서 Redis는 DB 일 **위에 더해져서** 느렸다. 이번에는 DB에 갈 일을 **대신하게** 하는 것이다.

### DECR

Redis에는 저장된 숫자를 1 줄이는 명령 `DECR`(decrement)이 있다. 늘리는 건 `INCR`, N만큼 줄이는 건 `DECRBY`다.

```text
SET  stock:product:1 100   → 100 저장 (딜 오픈 전에 미리 넣어 둔다)
DECR stock:product:1       → 99  (줄이고, 줄인 결과를 바로 돌려준다)
DECR stock:product:1       → 98
```

이걸 쓰는 이유는 **읽기 → 빼기 → 쓰기를 명령 하나로 끝내서**다. #03에서 두 사람이 재고 100을 동시에 읽고 둘 다 99를 써서 하나가 사라진 걸 봤다(갱신 손실). Redis는 명령을 하나씩 처리하니까, 1,000명이 동시에 DECR해도 99, 98, 97… 순서대로 하나씩 나오고, 같은 숫자를 받는 사람이 없다.

| | 원자적 UPDATE | Redis DECR |
|---|---|---|
| 하는 일 | `stock = stock - 1` | 숫자 - 1 |
| 거치는 것 | 직원 → 창구 → 장부 사용권 → 롤백/커밋 | 직원 → 안내판에 명령 하나 |
| 재고 확인 | `WHERE stock >= 1`이 해 준다 | **안 해 준다** (0 아래로도 내려간다) |

마지막 줄이 나중에 문제가 된다.

### 처음 버전

```java
public Order placeOrder(Long userId, Long productId, int quantity) {
    long left = stockCounter.decrease(productId, quantity);   // Redis: DECRBY
    if (left < 0) {
        throw new OutOfStockException(...);                   // DB에 안 가고 바로 품절
    }
    // 0 이상인 100명만 기존 원자적 UPDATE로 → 결제
    ...
}
```

통과한 100명은 여전히 DB에서 원자적 UPDATE를 한다. Redis 숫자가 혹시 틀려도 DB가 한 번 더 지켜 주게 남겨 뒀다. 그리고 결제가 실패했을 때 Redis 숫자를 되돌리는 처리는 **일부러 빼 뒀다.** 순진하게 짜면 어떻게 깨지는지 먼저 보고 싶었다.

### 처음 버전 측정

| 수치 (1,500 → 3,000) | 원자적 UPDATE만 | Redis DECR |
|---|---|---|
| 품절 응답 p95 | 568~644ms | **0.94ms** |
| 다른 상품 조회 p95 | 560~634ms | **4.02ms** |
| 3,000 구간 처리량 (초당) | 2,766 | 2,997 |
| DB UPDATE / ROLLBACK | 238,770 / 238,570 | **200 / 0** |
| 장부 사용권 대기 | 141,897번 | **0번** |
| 사용 중인 창구 (최대) | 10개 | 1개 |
| MySQL CPU | 약 60% | 약 2% |

DB UPDATE 200번은 판매된 100건의 재고 차감과 주문 상태 변경이다. **품절 손님은 DB에 한 번도 가지 않았다.**

300 → 900으로도 한 번 돌렸는데, 그때는 원자적 UPDATE만 쓸 때 3.51ms였던 다른 상품 조회 p95가 8.91ms로 오히려 나빠졌다. 그런데 조회는 Redis를 거치지 않고, 같은 버전을 1,500 → 3,000으로 돌렸을 때는 4.02ms였다. 한 번씩만 잰 값이라 흔들림으로 보고 원인을 찾지 않았다.

그리고 테스트가 끝난 뒤 Redis 숫자를 보니 **-247,272**였다. 품절 손님마다 1씩 더 내려간 값이 그대로 남은 것이다. 수량 1짜리 주문만 있으면 어차피 품절이라 티가 안 났다.

## 결제가 실패하면 팔 수 있는 재고가 남는 문제

결제 실패율을 20%로 올리고 같은 테스트를 돌렸다. 결제가 실패하면 DB 재고는 원래 코드가 별도 트랜잭션으로 다시 늘려 준다(보상 트랜잭션). 하지만 Redis 숫자는 아무도 되돌리지 않는다.

### 계속 몰릴 때

비교하려고 Redis를 붙이기 전 버전(원자적 UPDATE만)도 같은 조건으로 쟀다.

| 300 → 900 RPS, 결제 20% 실패 | 원자적 UPDATE만 | Redis DECR |
|---|---|---|
| 판매 | **100** | **81** |
| 결제 실패 | 22 | 19 |
| 테스트가 끝날 때 DB 남은 재고 | 0 | **19** |
| Redis 숫자 | — | -101,146 |
| 기존 장부 검사 (남은 재고 + 판매 = 100) | 통과 | **통과** |

Redis를 붙이기 전 버전은 결제 실패로 돌아온 재고 22개를 뒤에 온 손님이 바로 사 갔다. 첫 판매부터 마지막 판매까지 약 4초였다.

Redis 버전은 안내판이 딱 100명만 들여보내고 나머지를 다 돌려보낸다. 결제가 실패한 19개는 장부에는 돌아왔지만 안내판은 여전히 "0 아래"라서, **3분 내내 10만 명이 "품절"을 듣는 동안 19개가 그대로 남았다.**

더 무서운 건 표의 마지막 줄이었다. 매번 돌리던 장부 검사(남은 재고 + 판매 = 100)가 **통과했다.** 장부 안의 숫자끼리는 맞기 때문이다. 어긋난 건 장부와 안내판 사이였다. 저장소가 두 개가 되니 "둘이 같은가"를 따로 확인해야 했다. 그래서 테스트 끝에 "DB 재고 = Redis 숫자"인지 확인하는 검사를 추가했다.

### 한꺼번에 몰렸다가 끝날 때 (스파이크)

처음엔 재고 100개에 300명이 한 번씩 주문하는 장면(스파이크)으로 이 문제를 보여 주려고 했다. 그런데 결과가 예상과 달랐다.

| 회차 | 원자적 UPDATE만: 판매 / 남은 재고 | Redis DECR: 판매 / 남은 재고 |
|---|---|---|
| 1 | 88 / 12 | 78 / 22 |
| 2 | 81 / 19 | 83 / 17 |
| 3 | 81 / 19 | 80 / 20 |

**Redis가 없어도 재고가 남았다.** 300명이 거의 동시에 들어오고 결제에 0.3초가 걸리니, 결제 실패로 재고가 돌아올 때쯤엔 나머지 손님이 이미 "품절"을 듣고 떠난 뒤였다. Redis 버전 결과만 봤다면 Redis 탓이 아닌 걸 Redis 탓으로 썼을 것 같다. 이 문제는 **손님이 계속 들어올 때만** 차이가 났다.

## 해결: 되돌리기와 Lua 스크립트

### 되돌리는 순서

결제가 실패하거나 DB 처리 중 오류가 나면 Redis 숫자도 `INCRBY`로 되돌리게 했다. 이때 순서를 하나 정했다.

- **줄일 때는 Redis 먼저**, DB 나중
- **되돌릴 때는 DB 먼저**, Redis 나중

반대로 Redis를 먼저 늘리면, DB 재고가 아직 안 돌아온 순간에 새 손님이 안내판을 통과해서 창구까지 갔다가 "재고 없음"을 받을 수 있다. 이 순서를 지키면 **안내판 숫자가 장부보다 커지는 순간이 없다.**

### DECR 후 음수면 INCR: 재고가 남았는데 거절

되돌리기만으로는 부족했다. 처음 버전처럼 품절 손님마다 숫자가 내려가 -101,146이 돼 있으면, 결제 실패로 1을 되돌려도 여전히 음수라서 아무도 못 산다. 그래서 숫자가 0 아래로 내려가는 것 자체를 막아야 했다. 처음 떠오른 건 "DECRBY 결과가 음수면 바로 INCRBY로 되돌리기"였다.

```java
Long left = redis.opsForValue().decrement(key, quantity);   // 명령 ①
if (left < 0) {
    redis.opsForValue().increment(key, quantity);           // 명령 ②
    return false;
}
return true;
```

그런데 지난 글에서 본 "확인과 삭제를 따로 보내면 그 사이에 남이 끼어든다"가 떠올랐다. 이것도 명령 두 개다. 수량이 섞이면 이런 일이 생길 수 있다.

| 순서 | 일어나는 일 | 안내판 |
|---|---|---|
| 0 | 재고 1개 남음 | 1 |
| 1 | A가 3개 주문 → ① | -2 |
| 2 | B가 1개 주문 → ① → 음수라서 **거절** | -3 |
| 3 | A가 ② (3 되돌림) | 0 |
| 4 | B가 ② (1 되돌림) | 1 |

재고 1개가 남아 있는데 1개짜리 주문을 거절했다. 부하 테스트는 수량 1로만 보내서 이 장면이 안 나온다. 수량이 1이면 숫자가 음수가 되는 순간 실제로도 재고가 0이라, 거절해도 틀린 게 아니기 때문이다. 그래서 테스트를 따로 만들었다. 재고 10개에 40명(절반은 3개, 절반은 1개)이 동시에 주문하는 걸 200번 반복했다. 재고는 늘어나지 않으니, 1개짜리 주문이 거절됐다면 끝났을 때 재고는 0이어야 한다.

| 방식 | 재고가 남았는데 1개짜리 주문을 거절한 횟수 |
|---|---|
| DECR 후 음수면 INCR | **183 / 200** |

거의 매번 일어났다.

### Lua로 묶은 확인과 줄이기

지난 글의 락 풀기와 같은 방법을 썼다. Lua는 Redis 안에서 돌릴 수 있는 작은 프로그래밍 언어인데, 이걸로 "남은 수량이 충분하면 줄여 줘"를 스크립트 하나로 묶어 보낸다. 아래에서 `KEYS[1]`은 키 이름(`stock:product:1`), `ARGV[1]`은 주문 수량이다.

```lua
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil or stock < tonumber(ARGV[1]) then
    return 0                               -- 모자라거나 키가 없으면 건드리지 않음
end
redis.call('decrby', KEYS[1], ARGV[1])
return 1
```

Redis는 스크립트 하나를 끝까지 실행한 뒤에야 다음 명령을 처리한다. 그래서 확인과 줄이기 사이에 아무도 끼어들지 못하고, 숫자가 음수로 내려가지도 않는다. `WHERE stock >= 1`이 붙은 원자적 UPDATE를 Redis에서 한 셈이다.

| 방식 | 재고가 남았는데 1개짜리 주문을 거절한 횟수 |
|---|---|
| DECR 후 음수면 INCR | 183 / 200 |
| Lua | **0 / 200** |

정리하다 보니 #03, #04와 또 같은 모양이었다.

| | 나눠서 하면 깨짐 | 한 번에 하면 안전 |
|---|---|---|
| #03 재고 차감 | SELECT → 자바에서 계산 → UPDATE | `UPDATE ... WHERE stock >= 1` |
| #04 락 풀기 | GET → 자바에서 확인 → DEL | Lua 스크립트 |
| #05 Redis 재고 | DECRBY → 자바에서 확인 → INCRBY | Lua 스크립트 |

명령 하나하나는 끼어들 틈이 없어도, **두 명령 사이**에는 틈이 있었다.

## 아직 남은 구멍

다 막은 건 아니다. 알고 넘어가는 구멍이 두 개 있다.

1. **되돌리기 전에 서버가 죽으면** Redis 숫자가 DB보다 작게 남는다. 덜 팔리는 쪽이라 초과 판매는 안 생기지만, 팔 수 있는 걸 못 판다. 이건 결제와 재고를 서로 다른 곳에서 처리할 때 생기는 더 큰 문제와 같은 종류다. 멱등성(같은 요청이 여러 번 와도 한 번만 처리하기)과 사가(여러 단계 중 하나가 실패하면 앞 단계를 되돌리기)를 다룰 때 다시 볼 생각이다.
2. **Redis 디스크 저장을 꺼 둔 상태다.** 분산 락을 만들 때, 락은 잠깐 쓰고 버리는 값이라 Redis가 디스크에 저장하지 않게 꺼 뒀었다(글에는 쓰지 않은 설정이다). 그런데 이제 Redis가 재고 숫자를 들고 있다. Redis가 재시작되면 키가 사라지고, 키가 없으면 품절로 처리하게 해 뒀으니 모든 주문이 품절이 된다. 측정 조건을 바꾸지 않으려고 이번엔 그대로 뒀다.

DB를 아예 빼고 Redis만 믿으면 더 빠르겠지만, 그러면 Redis가 재시작될 때 재고 자체가 사라진다. 그래서 진짜 장부는 DB에 두고, Redis는 입구에서 걸러 주는 역할만 맡겼다.

> **정리**: 지난 글에서 Redis는 DB 일 위에 더해져서 느렸고, 이번에는 DB 일을 대신해서 빨라졌다. 대신 저장소가 둘이 되니 "둘이 같은가"를 따로 지켜야 했다. 실패하면 되돌리고, 확인과 줄이기는 한 번에 하고, 검사도 둘을 비교하게 바꿨다.
