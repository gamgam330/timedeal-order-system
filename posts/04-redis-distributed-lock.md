# [타임딜 #04] 분산 락을 걸었는데 300명이 샀다 — Redis 분산 락 vs 비관적 락

> **이번 글 요약**
> Redis 분산 락을 붙였더니 처음에는 **재고 100개에 300명이 샀다.** 락은 300번 다 정상으로 잡혔는데도 그랬다. 락이 **커밋보다 먼저** 풀리고 있었다.
>
> | 방식 | 재고 100개, 300명 | 인기 상품 초당 600건 + 다른 상품 조회 |
> |---|---|---|
> | Redis 락 (트랜잭션 안에서 해제) | **최대 300명 성공** ❌ | — |
> | Redis 락 (트랜잭션을 감쌈) | 100명 성공, 재고 0 ✅ | 처리 **약 310건/초**, 조회 p95 **4.5초** ❌ |
> | 비관적 락 | 100명 성공, 재고 0 ✅ | 처리 600건/초, 조회 p95 10ms ✅ |
> | 원자적 UPDATE | 100명 성공, 재고 0 ✅ | 처리 600건/초, 조회 p95 10ms ✅ |
>
> 분산 락은 DB 커넥션을 하나도 기다리게 하지 않았다. 그런데도 다른 요청이 더 느려졌다.

---

## Redis 분산 락을 써 본 이유

[지난 글(#03)](https://90000e.tistory.com/22)에서 재고 차감은 원자적 UPDATE(`stock = stock - 1 WHERE stock >= 1`)로 정리했다. 그런데 정리하면서 한 가지가 걸렸다. 재고 규칙이 WHERE 한 줄로 안 써지면(쿠폰, 등급별 한도 같은 것) 결국 비관적 락으로 가야 한다. 그리고 비관적 락은 **줄을 서 있는 동안에도 DB 커넥션을 쥐고 있다.**

커넥션이 10개뿐인데 10명이 한 상품 앞에 줄을 서면, 상관없는 다른 API도 커넥션을 못 받는다. #01에서 커넥션 고갈로 한 번 크게 데였던 터라 이게 신경 쓰였다.

자주 들어 본 **Redis 분산 락**이 떠올랐다. 줄을 DB가 아니라 Redis에서 서게 하면 커넥션은 안 쥐고 기다릴 수 있지 않을까 싶었다.

> **분산 락이란?**
> 서버가 여러 대일 때 `synchronized` 같은 자바 락은 **그 서버 안에서만** 통한다. 모든 서버가 같이 보는 곳(Redis)에 "지금 2번 상품은 내가 쓰는 중"이라는 표시를 남기는 방식이 분산 락이다.

## 직접 만든 Redis 락

Redisson 같은 라이브러리도 있지만, 안에서 무슨 일이 일어나는지 보려고 Redis 명령어로 직접 만들어 봤다.

```java
// 획득: 키가 없을 때만(NX) 저장하고, 3초 뒤 자동으로 지워지게(PX) 한다
redisTemplate.opsForValue().setIfAbsent("lock:product:2", token, Duration.ofSeconds(3));

// 해제: 내가 넣은 token일 때만 지운다 (Lua 스크립트로 비교와 삭제를 한 번에)
if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end
```

만들면서 알게 된 것들:
- **NX**: 키가 없을 때만 저장된다. 여러 서버가 동시에 시도해도 한 명만 성공한다.
- **TTL(3초)**: 락을 쥔 서버가 죽어도 3초 뒤에는 풀린다. 없으면 그 상품은 영원히 잠긴다.
- **token 확인**: 내 작업이 3초를 넘기면 락이 만료되고, 그사이 다른 요청이 새로 락을 잡을 수 있다. 그때 내가 그냥 지우면 **남의 락을 지운다.** 그래서 내 token일 때만 지운다.
- **Lua로 한 번에**: "확인"과 "삭제"를 따로 보내면 그 사이에 키가 바뀔 수 있다. Lua 스크립트는 Redis 안에서 끼어들기 없이 한 번에 실행된다.
- 락을 못 잡으면 10ms 쉬고 다시 시도하고, 5초가 지나면 포기한다(스핀 락).

## 락은 300번 잡혔는데 300명이 산 이유

처음엔 재고 차감 메서드 안에서 락을 잡았다. 재고 계산은 #03 이전처럼 엔티티에서 한다(읽고, 계산하고, 덮어쓰기).

```java
@Transactional
public Product decreaseStock(Long productId, int quantity) {
    return redisLock.executeWithLock("lock:product:" + productId, () -> {
        Product product = getProduct(productId);
        product.decreaseStock(quantity);
        return product;
    });
}
```

깔끔해 보였다. 그런데 테스트부터 깨졌다.

```text
OrderConcurrencyTest > 동시에_주문해도_재고보다_많이_팔리지_않는다()  FAILED
    [주문 성공] expected: 50  but was: 100
```

K6로 타임딜 오픈 테스트(재고 100개, 300명 동시 주문)도 돌려 봤다.

| 회차 | 주문 성공 | 품절 응답 | 남은 재고 | 초과 판매 |
|---|---|---|---|---|
| 1회 | **248** | 52 | 0 | 148 |
| 2회 | **299** | 1 | 0 | 199 |
| 3회 | **300** | 0 | 23 | 223 |

#03의 "락 없음"보다 오히려 더 많이 팔렸다. 이상한 건 락 지표였다. **락은 900번(회차당 300번) 정상적으로 잡히고 풀렸다.** 락이 고장 난 건 아니었다.

### 한 요청의 실제 순서

코드 순서 말고 실제로 일이 일어나는 순서를 적어 보니 보였다.

```text
[트랜잭션 시작]
  → Redis 락 획득
  → SELECT stock   (100)
  → stock = 99     ← 엔티티 필드만 바뀜. SQL은 아직 안 나감
  → Redis 락 해제  ← 여기서 다음 요청이 들어온다
  → INSERT orders
[커밋]  ← 이때 비로소 UPDATE product SET stock = 99
```

락이 풀리는 시점에 DB에는 아직 아무것도 반영되지 않았다. 다음 요청은 락을 잡고 들어와서 **여전히 100을 읽는다.** 락이 지켜 준 건 "SELECT 한 줄"뿐이었다.

### saveAndFlush로 고치려다 실패

처음엔 "UPDATE가 늦게 나가는 게 문제면 락 안에서 바로 내보내면 되지 않나?" 싶었다. 흔히 보이는 수정이라 직접 해 봤다.

```java
product.decreaseStock(quantity);
productRepository.saveAndFlush(product);   // UPDATE를 락 안에서 실행
```

| | 테스트 (재고 50, 100명) | 스파이크 (재고 100, 300명) |
|---|---|---|
| saveAndFlush 추가 | 96명 성공 ❌ | 197개, 179개 판매 ❌ |

줄기만 했다. UPDATE는 락 안에서 나갔지만 **커밋**은 여전히 락이 풀린 뒤였다.

- 다음 요청이 락을 잡고 SELECT하면, 앞 요청이 아직 커밋 전이라 **예전 값(100)** 이 보인다. (#03에서 본 REPEATABLE READ의 스냅샷 읽기)
- 그 요청의 UPDATE는 앞 요청이 잡은 행 락 때문에 잠깐 기다렸다가, 앞 요청이 커밋하면 **예전 값으로 계산한 99**를 덮어쓴다.

> **정리**: 락이 풀리는 시점이 커밋보다 빠르면, 락은 아무것도 지키지 못한다. 다음 사람은 아직 확정되지 않은 데이터를 넘겨받는다.

## 해결: 락이 트랜잭션을 감싸는 구조

순서를 **락 획득 → 트랜잭션 시작 → 커밋 → 락 해제**로 바꿨다. 락을 `OrderService`로 올려서 트랜잭션 전체를 감쌌다.

```java
String lockKey = ProductService.stockLockKey(productId);
Order order = redisLock.executeWithLock(lockKey, () -> transactionTemplate.execute(status -> {
    Product product = productService.decreaseStock(productId, quantity);
    return orderRepository.save(Order.create(userId, productId, quantity, product.getPrice()));
}));
```

결제가 실패해서 재고를 되돌리는 트랜잭션도 같은 락으로 감쌌다. #03에서 배운 것처럼, 차감만 지키고 복구를 안 지키면 복구에서 갱신 손실이 난다.

| 고민한 방법 | 판단 |
|---|---|
| **락으로 트랜잭션 전체를 감쌈 (선택)** | 커밋이 끝난 뒤 락이 풀린다. 덤으로 락을 **트랜잭션 밖에서** 기다리니까, 기다리는 동안 커넥션을 안 쥔다 |
| 커밋 후 콜백(`afterCompletion`)에서 해제 | 커밋 뒤에 풀리긴 한다. 하지만 락을 트랜잭션 안에서 잡으니 기다리는 동안 커넥션을 쥔다 |
| Redisson으로 교체 | 락 자체는 좋아지지만 "어디서 풀리느냐"는 그대로라 같은 버그가 난다 |

```text
OrderConcurrencyTest > 동시에_주문해도_재고보다_많이_팔리지_않는다()  PASSED
```

| 방식 (재고 100, 300명, 3회) | 성공 / 품절 | 남은 재고 | p95 |
|---|---|---|---|
| Redis 락 (트랜잭션을 감쌈) | 100 / 200 | 0 ✅ | 0.87~1.75초 |
| 비관적 락 | 100 / 200 | 0 ✅ | 0.52~0.68초 |
| 원자적 UPDATE | 100 / 200 | 0 ✅ | 0.45~0.71초 |

재고는 맞췄다. 다만 Redis 락만 확실히 느렸다. 품절 응답을 받을 200명도 전부 락 줄을 서야 하기 때문이다.

(Redis 컨테이너가 같은 맥의 CPU를 나눠 쓰게 돼서, 비관적 락과 원자적 UPDATE도 이번 환경에서 다시 쟀다.)

## 원래 확인하려던 것: 커넥션을 안 쥐면 다른 요청이 빨라지는가

이번 글을 시작한 이유를 확인할 차례다. 인기 상품 주문만 보내면 "커넥션을 안 쥔다"는 차이가 드러나지 않는다. 그래서 테스트를 하나 새로 만들었다.

- 인기 상품(2번) 주문: 초당 300 → 600 → 900건으로 올린다
- 그동안 **상관없는 상품 조회**(`GET /api/products/1`)를 초당 50건 같이 보낸다
- 락 대기만 보이도록 가짜 결제 지연은 0으로 둔다

내 예상은 이랬다. 비관적 락은 대기자가 커넥션을 다 차지해서 조회도 같이 느려지고, Redis 락은 조회가 멀쩡할 것이다.

> **RPS와 TPS** (#03에서도 쓴 표현)
> - **RPS**: K6가 초당 **보낸** 요청 수
> - **TPS**: 서버가 초당 **처리해 낸** 주문 수

| 방식 | 보낸 주문 (RPS) | 처리한 주문 (TPS) | Tomcat 스레드 사용 (최대 200) | 커넥션 대기 | 조회 p95 |
|---|---|---|---|---|---|
| Redis 락 | 300 | 300 | 69 | 0 | 10ms |
| | **600** | **약 310** | **200 (전부)** | **0** | **4.5초** |
| | 900 | 약 400 | 200 | 0 | 4.5초 |
| 비관적 락 | 300 | 300 | 1 | 0 | 10ms |
| | 600 | 600 | 43 | 33 | 10ms |
| | 900 | 약 840 | 200 | 190 | 1.7초 |
| 원자적 UPDATE | 300 | 300 | 3 | 0 | 10ms |
| | 600 | 600 | 33 | 24 | 10ms 미만 |
| | 900 | 약 760 | 200 | 190 | 1.8초 |

(두 번 돌렸고 모양은 같았다. 위 표는 2회차.)

**절반은 맞고 절반은 틀렸다.**

- 맞은 것: Redis 락은 정말로 커넥션을 기다리게 하지 않았다. 커넥션 대기는 끝까지 0, 동시에 쓴 커넥션도 최대 3개였다.
- 틀린 것: 그런데도 **조회가 가장 먼저, 가장 크게 느려졌다.** 비관적 락은 600건까지 조회가 10ms였는데, Redis 락은 600건에서 4.5초였다.

### 줄이 커넥션 풀에서 Tomcat 스레드로 이동

Tomcat 스레드 그래프를 보고 이해가 됐다.

![Redis 락 Tomcat 스레드](images/step03-mixed-redislock/tomcat-threads.png)

Redis 락은 초당 약 310건에서 더 처리하지 못했고, 처리 못 한 주문들이 **Tomcat 스레드를 하나씩 쥔 채** 락을 기다렸다. 스레드 200개가 다 차자 조회 요청은 커넥션이 아니라 **스레드**를 못 받아서 기다렸다.

![비관적 락 커넥션](images/step03-mixed-pessimistic/hikari-connections.png)

비관적 락은 600건까지는 커넥션 대기가 잠깐 튀는 정도였고, 900건에서야 커넥션 대기 190이 찼다.

결국 **줄 서는 장소만 바뀌었다.** 커넥션 풀이든 Tomcat 스레드든 모든 요청이 같이 쓰는 자원이라, 줄이 넘치면 상관없는 요청도 같이 막힌다.

> **은행 창구 비유로 다시 보면**
> - 비관적 락: 창구(커넥션) 앞에서 번호표를 들고 기다린다. 창구가 다 차면 다른 업무 손님도 못 들어간다.
> - Redis 락: 창구는 비워 두고 **로비 의자(Tomcat 스레드)** 에 앉아서 기다린다. 그런데 의자가 200개뿐이라, 의자가 다 차면 다른 손님은 **건물에 들어오지도 못한다.**

### Redis 락이 초당 300건에서 막힌 이유

비관적 락은 600건을 처리했는데 Redis 락은 왜 절반이었을까. 락을 쥐고 있는 동안 무엇을 하는지 비교해 보니 차이가 있었다.

```text
Redis 락이 잠그는 구간:
  SET NX(왕복) → 커넥션 빌림 → 트랜잭션 시작 → SELECT, INSERT, UPDATE → 커밋 → 커넥션 반납 → Lua 해제(왕복)

비관적 락이 잠그는 구간:
  SELECT ... FOR UPDATE → INSERT, UPDATE → 커밋
```

- 커넥션을 쓴 시간은 주문당 약 1.7ms인데, 초당 300건이면 락 한 번에 약 3.3ms다. 나머지 약 1.6ms는 **Redis 왕복과 트랜잭션 준비처럼 DB 밖에서 쓴 시간**이다. 그동안에도 아무도 재고를 못 만진다.
- 비관적 락의 대기자는 이미 커넥션을 쥐고 트랜잭션을 연 채로 DB 안에서 기다린다. 앞사람이 커밋하면 바로 이어 받는다. 커넥션을 쥐고 기다리는 게 단점인 줄만 알았는데, 이어 받는 속도에서는 장점이었다.
- 스핀 대기에도 비용이 있었다. 대기자 200명이 10ms마다 "락 비었어?"를 물어서 Redis에 **초당 약 1만 8천 번** 요청이 갔다. 실제로 락을 얻은 건 초당 300~400번이다.

## 최종 선택: 재고 차감은 원자적 UPDATE 유지

정합성 버그(락이 커밋보다 먼저 풀림)는 고쳤다. 하지만 **이 프로젝트의 재고 차감에는 Redis 락을 쓰지 않기로 했다.** 지금 재고 규칙은 WHERE 한 줄로 되고, 그럴 때는 원자적 UPDATE가 처리량, 다른 요청의 지연, 코드 단순함 모두에서 나았다.

그럼 분산 락은 언제 쓰는 걸까. 찾아보고 오늘 결과를 겹쳐 보니 이렇게 정리됐다.
- 지키려는 게 **DB 행 하나가 아닐 때**: 외부 API 호출, 여러 저장소에 걸친 작업, 스케줄러가 여러 서버에서 동시에 도는 것 막기. 이런 건 DB 락으로 못 막는다.
- **기다리지 않고 바로 실패시킬 때**: 락을 못 잡으면 바로 "잠시 후 다시 시도"를 돌려주면 스레드가 쌓이지 않는다.
- 기다려야 한다면 스핀 대신 락이 풀릴 때 알려 주는 방식(Redisson의 pub/sub)을 써야 Redis에 1만 8천 번씩 묻지 않는다.

> **정리**: 분산 락은 "어디서 풀리느냐"를 잘못 잡으면 정합성이 깨지고, 제대로 잡아도 한 행에 몰리는 경합에서는 DB 락보다 느렸다. "커넥션을 안 쥔다"는 장점은 진짜였지만, 대기자가 스레드를 쥐고 있으니 줄 서는 장소만 바뀌었다.

## 남은 과제

이번 테스트에서 하나 더 보였다. 재고가 다 팔린 뒤에도 품절 응답을 받을 요청들이 **전부** 락 줄을 서거나 DB까지 간다. 재고 100개에 10만 명이 몰리면 99,900명이 "품절"이라는 한 마디를 듣기 위해 줄을 선다.

줄 서는 장소를 옮기는 게 아니라 **줄 자체를 없앨 수는 없을까.** 다음 글에서는 Redis에 재고 숫자 자체를 두고(DECR, Lua) 품절 요청을 DB 앞에서 돌려보내 볼 생각이다.
