# 001. 에러율 0%인데 p95가 38초: 커넥션 풀 앞에 숨은 대기열

- 단계: step01 / 날짜: 2026-10-21
- 원본 결과: `k6/results/step01-load-baseline-20261021-1951.*`, `k6/results/step01-spike-baseline-20261021-1956.*`

## 현상
load 시나리오 (`ramping-arrival-rate` 20 → 40 → 60 RPS, 주문 API)

| 지표 | 값 |
|---|---|
| 처리량 | 평균 26.8 TPS, 서버 기준 20 RPS 구간 19.8 / 40 RPS 구간 **33.0** (이론상 한계 33과 일치) |
| K6 응답 시간 | 중앙값 8.5초, **p95 38.1초**, 최대 44.7초 |
| 에러율 | **0%** (8034건 모두 201) |
| 버려진 요청 | dropped_iterations 1390 (VU 부족), 종료 시 interrupted 550 |
| SLO (p95 < 500ms) | ✗ 실패 |

## 가설
1. (사전 가설, AI) 커넥션 풀(10개)이 한계 → Hikari 대기가 30초(connectionTimeout)를 넘으면 `SQLTransientConnectionException`이 쏟아진다 → 에러율이 올라갈 것이다
2. 결과는 에러 0%인데 지연은 38초 → 30초를 넘게 기다렸는데 타임아웃이 안 났다면, **대기가 Hikari가 아닌 다른 곳에서 일어나고 있다**

## 검증 (Prometheus, 54:00 이전 구간)
| 지표 | 값 | 해석 |
|---|---|---|
| Hikari timeout 횟수 | 0 | 가설 1 기각 |
| Hikari pending 최대 | 189 | 커넥션을 기다리는 스레드가 189개 |
| Hikari 획득 시간 최대 | 12.2초 | 30초에 못 미침 |
| Hikari 점유 시간 평균 | 0.319초 | PG 300ms + 쿼리. 커넥션 하나가 초당 약 3건 |
| Tomcat busy 스레드 최대 | **200 / 200** | 스레드 풀 포화 |
| 서버 측 응답 시간 최대 | 12.5초 | |
| K6 측 응답 시간 p99 최대 | **41.4초** | 서버 측과 약 29초 차이 |

**결론: 대기열이 두 겹이었다.**
```
요청 → [Tomcat 대기열: 스레드를 기다림]  → [Hikari 대기열: 커넥션을 기다림] → DB + PG(300ms)
        서버 지표에 안 잡힘 (약 29초)          최대 189개, 최대 12초
```
- Tomcat 스레드가 200개뿐이라서, Hikari 앞에서 기다리는 요청은 최대 190개 정도로 제한된다 → Hikari 대기는 30초까지 가지 않는다.
- 나머지 요청은 **Tomcat 워커 스레드를 받기 전 단계**(NIO 커넥터는 최대 8192개 연결을 받아 둔다)에서 기다린다. 서버 타이머(`http.server.requests`)는 스레드가 요청을 집은 뒤에 시작되므로 이 대기는 **서버 지표에 보이지 않는다.**
- 결과적으로 에러는 0%인데 사용자는 40초를 기다린다. 실제 사용자는 3초 안에 이탈한다. **에러율만 보면 정상처럼 보이는 장애.**

## 부수 발견 (이후 단계 재료)
1. **모니터링이 가장 중요한 순간에 꺼졌다.** 10:54:15~10:56:15 동안 Prometheus 수집 실패(`up=0`, scrape_duration 5초 타임아웃). `/actuator/prometheus`도 같은 Tomcat 대기열에 줄을 섰기 때문이다. → 관리 포트 분리(`management.server.port`) 검토
2. **클라이언트는 포기했는데 서버는 결제까지 처리했다.** K6가 끝날 때 끊은 550건이 나중에 전부 처리되어 PAID 주문이 8034 → 8584건이 됐다. 사용자는 실패로 알고 재시도하면 중복 결제로 이어진다. → step07 멱등성
3. **갱신 손실(lost update)이 이미 일어나고 있다.**
   - load: 8584건이 결제됐는데 재고는 962개만 줄었다 (차이 7622)
   - spike: 재고 100개 상품에 **300건이 전부 성공**했고, 남은 재고는 **70개** (초과 판매 200건)
   - 동시에 열린 트랜잭션 10개가 같은 재고 값을 읽고 각자 덮어쓰기 때문이다. → step03 동시성

## 실패한 시도
1. **AI의 사전 가설이 틀렸다.** "30초 뒤 connectionTimeout 에러가 폭증한다"고 예측했지만, Tomcat 스레드 수가 Hikari 대기열의 길이를 제한한다는 점을 고려하지 않았다.
2. **첫 A 측정이 오염됐다.** 테스트 중 맥이 잠자기(Idle Sleep, 배터리 모드)에 들어가 요청 38건 EOF, 최대 응답 1분 39초가 나왔다. 앱 로그의 `Thread starvation or clock leap detected (housekeeper delta=2m6s)`와 `pmset -g log`로 원인을 확인하고 무효 처리했다 → `make k6`에 `caffeinate`를 추가했다.
3. **A. 풀 크기를 10에서 30으로 늘렸다 → 통과했지만, PG가 1초로 느려지자 다시 무너졌다.** 커넥션이 PG를 기다리는 구조가 그대로라서, 처리 한계가 `풀 크기 ÷ PG 지연`에 묶여 있다. PG 지연이 3배가 되면 풀도 3배가 필요하다. 근본 해결이 아니다.

## 해결
1. **D. 관리 포트 분리** (`management.server.port: 8081`): 지표 엔드포인트가 별도 Tomcat 커넥터와 스레드 풀을 쓴다 → 과부하 중에도 수집이 끊기지 않는다 (재측정 5회 모두 `up` 최솟값 1).
2. **B. 외부 PG 호출을 DB 트랜잭션 밖으로 뺐다** (풀 크기는 기본값 10 유지)
```
[트랜잭션1] 재고 예약 + 주문 PENDING → 커밋 (커넥션 반납)
PG 승인 요청 (커넥션 없음)
  성공 → [트랜잭션2] 결제 저장 + 주문 PAID
  실패 → [트랜잭션3] 재고 복구 + 주문 FAILED   ← 이미 커밋돼서 롤백할 수 없으므로 보상
```
- 같은 클래스의 `@Transactional` 메서드를 내부에서 부르면 프록시를 거치지 않아 적용되지 않으므로(self-invocation), `TransactionTemplate`으로 경계를 코드에 드러냈다.
- **새로 생긴 위험**: PG 승인 후 트랜잭션2가 실패하거나 그 사이 서버가 죽으면 결제는 됐는데 주문이 PENDING으로 남는다 → 07단계(멱등성), 08단계(사가)에서 다룬다.

### 다음 병목: 이제는 스레드다
B-1000에서 Tomcat busy가 61 = 60 RPS × 1초. 커넥션 대신 **스레드가 PG를 기다린다.** 스레드 200개 ÷ PG 1초 = 약 200 TPS가 다음 한계다. (가상 스레드, 비동기 호출, 타임아웃 설정이 후보)

## 배운 것
- 에러율 0%가 정상이라는 뜻은 아니다. 지연과 함께 봐야 한다.
- 서버 지표와 클라이언트 지표의 차이가 곧 "보이지 않는 대기열"이다. 둘을 한 화면에 둔 이유.
- 지표 수집 경로가 서비스 트래픽과 같은 자원을 쓰면, 과부하 때 관측도 같이 죽는다.
