# 004. 품절인데도 모든 요청이 DB까지 간다 (작성 중)

- 단계: step04 / 날짜: 2026-10-27~28
- 원본 결과: `k6/results/step04-soldout-*`
- 태그: `step-04-broken` → `step-04-fixed` (예정)

## 배경
03단계 결론으로 재고 차감은 원자적 UPDATE(`UPDATE … SET stock = stock - 1 WHERE id = ? AND stock >= 1`)로 되돌렸다. 정합성은 맞지만, 재고가 0이 된 뒤에도 "품절"을 들을 요청이 전부 이 UPDATE를 실행하고 0행을 받은 다음에야 409를 받는다.

## 현상
시나리오 `step04-soldout`: 재고 100개 상품(1번)에 주문을 계속 보냄. 다른 상품(2번) 조회를 초당 50건 함께 보냄. PG 지연 300ms(기본값), 앱 1대. K6도 같은 맥에서 돈다.

| 실행 | 주문 RPS | 판매 | 품절(409) | 품절 응답 p95 | 다른 상품 조회 p95 | 시작 못 한 요청 |
|---|---|---|---|---|---|---|
| atomic-r1 | 300 → 600 → 900 | 100 | 101,147 | 2.42ms | 3.51ms | 0 |
| atomic-high-r1 | 1500 → 3000 | 100 | 229,575 | 644ms | 634ms | 17,821 |
| atomic-high-r2 | 1500 → 3000 | 100 | 238,570 | 568ms | 560ms | 8,822 |

- 시작 못 한 요청: 응답이 늦어져 K6의 가상 사용자(최대 1,500명)가 모두 응답을 기다리는 바람에 보내지 못한 요청 (`dropped_iterations`)
- high-r1과 r2는 같은 조건인데 시작 못 한 요청 수가 두 배 차이 난다. 맥 한 대에서 K6와 앱이 함께 돌아서 생긴 흔들림으로 보고, 숫자보다 모양(3000 구간에서 둘 다 느려짐)을 본다

같은 시간 동안 DB가 실행한 문장 수 (`SHOW GLOBAL STATUS` 차이):

| 실행 | UPDATE | SELECT | ROLLBACK | 행 락 대기 횟수 | 행 락 대기 시간 합계 |
|---|---|---|---|---|---|
| atomic-r1 | 101,347 | 110,349 | 101,147 | (안 잼) | (안 잼) |
| atomic-high-r2 | 238,770 | 244,772 | 238,570 | 141,897 | 386초 |

- 품절 요청 1건마다 UPDATE(0행) 1번 + SELECT 1번(예외 메시지에 넣을 재고 조회) + ROLLBACK 1번이 실행됨
  - 확인: atomic-r1의 UPDATE 101,347 = 품절 101,147 + 판매 100(재고) + 100(주문 PAID). SELECT 110,349 ≈ 품절 101,147 + 조회 9,001 + 판매 쪽 200
- 초당 900건까지는 응답이 빨랐다. 문제는 지연이 아니라 **DB 작업량**으로만 보였다
- 3000 구간에서는 상관없는 상품 조회도 p95 0.6초로 같이 느려졌다

## 가설
1. 품절 요청이 커넥션 10개를 나눠 쓰느라, 조회 요청도 커넥션을 기다린다
2. MySQL CPU가 한계에 닿았다
3. 품절 UPDATE들이 1번 상품 행의 X락을 순서대로 기다린다. 재고가 0이어도 UPDATE는 행을 찾아 락을 건 뒤 WHERE를 평가하고, MySQL 기본 격리 수준(REPEATABLE READ)에서는 조건에 안 맞은 행의 락도 트랜잭션이 끝날 때(ROLLBACK)까지 쥔다

## 검증
atomic-high-r2의 구간별 Prometheus 지표 (각 구간 끝 직전 30초):

| 지표 | 1500 구간 | 3000 구간 |
|---|---|---|
| 앱이 처리한 주문 요청 (초당) | 1,500 | 2,766 (목표 3,000) |
| 커넥션 1회 사용 시간 평균 | 0.8ms | **3.5ms** |
| 사용 중인 커넥션 (평균) | 1.3개 | 10개 (전부) |
| 커넥션을 기다리는 요청 (최대) | 0 | 190 |
| 사용 중인 Tomcat 스레드 (최대) | 2 | 200 (전부) |

- 가설 2는 아님: `docker stats` 기준 MySQL CPU는 3000 구간에서 약 60% (CPU 2개 제한이라 최대 200%)
- 가설 3이 맞음: UPDATE 238,770번 중 141,897번(59%)이 행 락을 기다렸고, 기다린 시간이 합계 386초(한 번에 평균 2.7ms)
- 가설 1은 결과로 나타난 현상: 커넥션 1회 사용 시간이 0.8ms → 3.5ms로 늘어난 건 커넥션을 쥔 채 DB 안에서 행 락을 기다렸기 때문이다. 커넥션 10개 ÷ 3.5ms ≈ 초당 2,860건이 이 구조의 한계이고, 실제 처리량 2,766과 맞는다
- 정리: **줄은 커넥션 풀과 Tomcat 스레드 앞에 섰지만, 줄이 생긴 이유는 DB 안의 행 락 대기였다.** CPU를 쓰지 않고 기다리기 때문에 CPU만 보면 DB가 한가해 보인다
