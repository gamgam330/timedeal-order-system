# 004. 품절인데도 모든 요청이 DB까지 간다

- 단계: step04 / 날짜: 2026-10-27~28
- 원본 결과: `k6/results/step04-soldout-*`
- 태그: `step-04-broken` (DECR, 되돌리기 없음) → `step-04-fixed` (Lua + 되돌리기)

## 배경
03단계 결론으로 재고 차감은 원자적 UPDATE(`UPDATE … SET stock = stock - 1 WHERE id = ? AND stock >= 1`)로 되돌렸다. 정합성은 맞지만, 재고가 0이 된 뒤에도 "품절"을 들을 요청이 전부 이 UPDATE를 실행하고 0행을 받은 다음에야 409를 받는다.

## 현상
시나리오 `step04-soldout`: 재고 100개 상품(1번)에 주문을 계속 보냄. 다른 상품(2번) 조회를 초당 50건 함께 보냄. PG 지연 300ms(기본값), 앱 1대. K6도 같은 맥에서 돈다.

| 실행 | 주문 RPS | 판매 | 품절(409) | 품절 응답 p95 | 다른 상품 조회 p95 | 시작 못 한 요청 |
|---|---|---|---|---|---|---|
| atomic-r1 | 300 → 600 → 900 | 100 | 101,147 | 2.42ms | 3.51ms | 0 |
| atomic-high-r1 | 1500 → 3000 | 100 | 229,575 | 644ms | 634ms | 17,821 |
| atomic-high-r2 | 1500 → 3000 | 100 | 238,570 | 568ms | 560ms | 8,822 |

- 시작 못 한 요청: 응답이 늦어져 K6의 가상 사용자(최대 1,500명)가 모두 응답을 기다리는 바람에 보내지 못한 요청 (`dropped_iterations`)
- high-r1과 r2는 같은 조건인데 시작 못 한 요청 수가 두 배 차이 난다. 맥 한 대에서 K6와 앱이 함께 돌아서 생긴 흔들림으로 보고, 숫자보다 모양(3000 구간에서 둘 다 느려짐)을 본다

같은 시간 동안 DB가 실행한 문장 수 (`SHOW GLOBAL STATUS` 차이):

| 실행 | UPDATE | SELECT | ROLLBACK | 행 락 대기 횟수 | 행 락 대기 시간 합계 |
|---|---|---|---|---|---|
| atomic-r1 | 101,347 | 110,349 | 101,147 | (안 잼) | (안 잼) |
| atomic-high-r2 | 238,770 | 244,772 | 238,570 | 141,897 | 386초 |

- 품절 요청 1건마다 UPDATE(0행) 1번 + SELECT 1번(예외 메시지에 넣을 재고 조회) + ROLLBACK 1번이 실행됨
  - 확인: atomic-r1의 UPDATE 101,347 = 품절 101,147 + 판매 100(재고) + 100(주문 PAID). SELECT 110,349 ≈ 품절 101,147 + 조회 9,001 + 판매 쪽 200
- 초당 900건까지는 응답이 빨랐다. 문제는 지연이 아니라 **DB 작업량**으로만 보였다
- 3000 구간에서는 상관없는 상품 조회도 p95 0.6초로 같이 느려졌다

## 가설
1. 품절 요청이 커넥션 10개를 나눠 쓰느라, 조회 요청도 커넥션을 기다린다
2. MySQL CPU가 한계에 닿았다
3. 품절 UPDATE들이 1번 상품 행의 X락을 순서대로 기다린다. 재고가 0이어도 UPDATE는 행을 찾아 락을 건 뒤 WHERE를 평가하고, MySQL 기본 격리 수준(REPEATABLE READ)에서는 조건에 안 맞은 행의 락도 트랜잭션이 끝날 때(ROLLBACK)까지 쥔다

## 검증
atomic-high-r2의 구간별 Prometheus 지표 (각 구간 끝 직전 30초):

| 지표 | 1500 구간 | 3000 구간 |
|---|---|---|
| 앱이 처리한 주문 요청 (초당) | 1,500 | 2,766 (목표 3,000) |
| 커넥션 1회 사용 시간 평균 | 0.8ms | **3.5ms** |
| 사용 중인 커넥션 (평균) | 1.3개 | 10개 (전부) |
| 커넥션을 기다리는 요청 (최대) | 0 | 190 |
| 사용 중인 Tomcat 스레드 (최대) | 2 | 200 (전부) |

- 가설 2는 아님: `docker stats` 기준 MySQL CPU는 3000 구간에서 약 60% (CPU 2개 제한이라 최대 200%)
- 가설 3이 맞음: UPDATE 238,770번 중 141,897번(59%)이 행 락을 기다렸고, 기다린 시간이 합계 386초(한 번에 평균 2.7ms)
- 가설 1은 결과로 나타난 현상: 커넥션 1회 사용 시간이 0.8ms → 3.5ms로 늘어난 건 커넥션을 쥔 채 DB 안에서 행 락을 기다렸기 때문이다. 커넥션 10개 ÷ 3.5ms ≈ 초당 2,860건이 이 구조의 한계이고, 실제 처리량 2,766과 맞는다
- 정리: **줄은 커넥션 풀과 Tomcat 스레드 앞에 섰지만, 줄이 생긴 이유는 DB 안의 행 락 대기였다.** CPU를 쓰지 않고 기다리기 때문에 CPU만 보면 DB가 한가해 보인다

## 실패한 시도
### DECR만 하고 되돌리지 않음 → 팔 수 있는 재고를 못 판다 (`step-04-broken`)
아래 "해결 > 1차"의 순진한 구현에서 PG 실패율만 20%로 올렸다 (`--pg.failure-rate=0.2`). 결제가 실패하면 트랜잭션3이 DB 재고는 되돌리지만 Redis 숫자는 그대로다.

**품절 폭주 (300→900 RPS, 3분)**: 두 방식이 갈렸다

| | 원자적 UPDATE만 | DECR (되돌리기 없음) |
|---|---|---|
| 판매 | **100** | 81 |
| 결제 실패 | 22 | 19 |
| 테스트가 끝날 때 DB 남은 재고 | 0 | **19** |
| 품절 응답 | 101,124 | 101,146 |
| Redis 숫자 | — | -101,146 |
| 기존 정합성 검사 (남은 재고 + 판매 − 100) | 0 | **0** |

- 원자적 UPDATE만 쓸 때: 결제 실패 22건으로 되돌린 재고를 뒤에 온 사람이 바로 사 갔다. 첫 판매부터 마지막 판매까지 약 4초
- DECR: Redis는 100명만 통과시키고 이후 요청을 모두 돌려보낸다. 결제가 실패한 19개는 DB에는 돌아왔지만 Redis를 통과할 방법이 없어서, **3분 동안 101,146명이 "품절"을 듣는 동안 19개가 팔리지 않고 남았다**
- 기존 정합성 검사는 0이라 문제를 못 잡는다. DB 장부(남은 재고 + 판매)는 맞기 때문이다. 깨진 건 **Redis 숫자와 DB 재고 사이**다

**스파이크 (재고 100, 300명이 한 번씩)**: 두 방식이 구분되지 않았다

| 회차 | 원자적 UPDATE만: 판매 / 남은 재고 | DECR: 판매 / 남은 재고 |
|---|---|---|
| 1 | 88 / 12 | 78 / 22 |
| 2 | 81 / 19 | 83 / 17 |
| 3 | 81 / 19 | 80 / 20 |

- 300명이 거의 동시에 들어오고 PG 지연이 300ms라, 결제 실패로 재고가 돌아올 때는 나머지가 이미 품절 응답을 받고 떠난 뒤다. 원자적 UPDATE만 써도 재고가 남는다
- 그래서 이 문제는 "주문이 계속 들어오는 동안"에만 차이가 난다. 처음에 스파이크로 보여 주려던 계획이 맞지 않았다

### 되돌리기를 넣고 DECR → 음수면 INCR → 재고가 남았는데 다른 주문을 거절한다
결제 실패 때 Redis도 되돌리게 한 뒤, 품절 요청이 남기는 음수를 없애려고 "DECRBY 결과가 음수면 바로 INCRBY로 되돌리기"를 넣었다.

```java
Long left = redis.opsForValue().decrement(key, quantity);   // 명령 ①
if (left < 0) {
    redis.opsForValue().increment(key, quantity);           // 명령 ②
    return false;
}
```

수량이 섞인 동시성 테스트(`StockCounterConcurrencyTest`): 재고 10에 40명(절반은 3개, 절반은 1개)이 동시에 주문, 200라운드.
재고는 늘어나지 않으므로 1개짜리 주문이 거절됐다면 끝났을 때 재고는 0이어야 한다.

| 방식 | 재고가 남았는데 1개짜리 주문을 거절한 라운드 |
|---|---|
| DECR → 음수면 INCR | **183 / 200** |
| Lua (확인 + 줄이기 한 번에) | 0 / 200 |

- 재고 1에서 3개짜리 주문이 ①을 실행하면 숫자가 -2가 된다. ②로 되돌리기 전에 1개짜리 주문이 ①을 실행하면 -3을 보고 거절된다. 그 뒤 ②가 실행되어 숫자는 1로 돌아오지만, 1개짜리 주문은 이미 "품절"을 받았다
- 03편의 "읽기 → 계산 → 쓰기 사이에 다른 요청이 끼어든다"와 같은 모양이다. 명령 하나하나는 원자적이어도, 두 명령 사이는 아니다
- 부하 테스트(수량 1만 보냄)에서는 이 문제가 드러나지 않는다. 수량이 1이면 음수가 된 순간에는 실제로도 재고가 0이기 때문이다

## 해결
### 1차: Redis DECR (순진한 구현)
- 딜 오픈 전에 Redis에 `stock:product:1 = 100`을 넣는다 (`make k6-reset`)
- 주문이 오면 트랜잭션1 전에 `DECRBY stock:product:1 <수량>`. 결과가 음수면 DB에 가지 않고 409
- 결과가 0 이상인 요청만 기존 원자적 UPDATE로 간다 (DB 재고도 함께 지킨다)
- 일부러 넣지 않은 것: 결제 실패나 DB 실패 때 Redis 숫자 되돌리기 (다음에 터뜨릴 문제)

### 최종: Lua로 확인 + 줄이기, 실패하면 되돌리기 (`step-04-fixed`)
```lua
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil or stock < tonumber(ARGV[1]) then return 0 end   -- 모자라거나 키 없음: 건드리지 않음
redis.call('decrby', KEYS[1], ARGV[1])
return 1
```

- 숫자가 음수로 내려가지 않는다. 확인과 줄이기 사이에 다른 명령이 끼어들지 않는다 (04편의 "Lua = Redis판 원자적 UPDATE")
- 되돌리기: 트랜잭션1이 실패하면 Redis만, PG가 실패하면 DB(트랜잭션3)를 되돌린 **뒤에** Redis를 `INCRBY`
- 순서 원칙: 줄일 때는 Redis 먼저, 되돌릴 때는 Redis 나중. Redis 숫자가 DB 재고보다 커지는 순간을 만들지 않는다. 그러면 Redis를 통과한 요청이 DB에서 재고 부족으로 실패하는 일이 없다
- 정합성 검사에 "Redis 숫자 = DB 재고" 비교를 추가했다 (`make k6` 끝에 OK / MISMATCH)

다른 선택지:
- DB 재고를 아예 없애고 Redis만 믿기: 더 빠르지만 Redis가 재시작되면 재고가 사라진다. DB를 진짜 장부로 두고 Redis는 앞에서 걸러 주는 역할만 맡겼다
- 주기적으로 DB 값을 Redis에 다시 맞추기: 딜 진행 중에 덮어쓰면 그 사이 예약된 수량이 꼬인다. 이번 범위에서 뺐다

알려진 한계:
- 되돌리기(`INCRBY`) 전에 서버가 죽으면 Redis가 DB보다 작게 남는다(덜 팔림). 더 팔리지는 않는다. 08~09단계(멱등성, 사가)와 이어진다
- Redis는 디스크 저장을 꺼 둔 상태다(03단계에 락 용도로 정함). 재시작되면 키가 사라지고 모든 주문이 품절로 처리된다. 측정 조건을 바꾸지 않으려고 이번에는 그대로 두었다

## 배운 것
- 품절 요청이 DB를 거치는 비용은 응답 시간이 아니라 DB 작업량과 행 락 대기로 먼저 나타났다. 한계에 닿자 줄은 커넥션 풀 앞에 섰지만 원인은 DB 안의 행 락이었다. CPU 그래프에는 락 대기가 안 보인다
- 03단계에서 Redis는 DB 작업 위에 더해져서 느렸고, 이번에는 DB 작업을 대신해서 빨라졌다
- 저장소가 두 개가 되면 "둘이 같은가"를 따로 확인해야 한다. 기존 정합성 검사(DB 장부)는 통과했는데 팔 수 있는 재고가 남아 있었다
- 명령 하나하나가 원자적이어도 두 명령 사이는 아니다. DECR + INCR은 03편의 갱신 손실과 같은 모양으로 깨졌다
- 비교 대상 없이 측정하면 원인을 잘못 짚는다. 스파이크에서 재고가 남은 건 Redis 탓이 아니었다
