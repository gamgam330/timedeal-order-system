# 004. 품절인데도 모든 요청이 DB까지 간다 (작성 중)

- 단계: step04 / 날짜: 2026-10-27
- 원본 결과: `k6/results/step04-soldout-*`
- 태그: `step-04-broken` → `step-04-fixed` (예정)

## 배경
03단계 결론으로 재고 차감은 원자적 UPDATE(`UPDATE … SET stock = stock - 1 WHERE id = ? AND stock >= 1`)로 되돌렸다. 정합성은 맞지만, 재고가 0이 된 뒤에도 "품절"을 들을 요청이 전부 이 UPDATE를 실행하고 0행을 받은 다음에야 409를 받는다.

## 현상
시나리오 `step04-soldout`: 재고 100개 상품(1번)에 주문을 계속 보냄. 다른 상품(2번) 조회를 초당 50건 함께 보냄. PG 지연 300ms(기본값), 앱 1대.

| 실행 | 주문 RPS | 판매 | 품절(409) | 품절 응답 p95 | 다른 상품 조회 p95 | 못 보낸 요청 |
|---|---|---|---|---|---|---|
| atomic-r1 | 300 → 600 → 900 | 100 | 101,147 | 2.42ms | 3.51ms | 0 |
| atomic-high-r1 | 1500 → 3000 | 100 | 229,575 | 644ms | 634ms | 17,821 |

같은 시간 동안 DB가 실행한 문장 수 (`SHOW GLOBAL STATUS` 차이):

| 실행 | UPDATE | SELECT | ROLLBACK | COMMIT |
|---|---|---|---|---|
| atomic-r1 | 101,347 | 110,349 | 101,147 | 9,201 |
| atomic-high-r1 | 229,775 | 235,777 | 229,575 | 6,201 |

- 품절 요청 1건마다 UPDATE(0행) 1번 + SELECT 1번(예외 메시지에 넣을 재고 조회) + ROLLBACK 1번이 실행됨
- 초당 900건까지는 응답이 빨랐다. 문제는 지연이 아니라 **DB 작업량**으로만 보였다
- 초당 1,500~3,000건에서는 앱이 초당 약 1,900건밖에 받지 못했다 (k6가 17,821건을 보내지 못함). 상관없는 상품 조회도 p95 0.6초로 같이 느려졌다

## 가설
1. 품절 요청이 커넥션 10개를 나눠 쓰느라, 조회 요청도 커넥션을 기다린다
2. MySQL CPU가 한계에 닿았다
3. 품절 UPDATE들이 1번 상품 행의 X락을 순서대로 기다린다 (재고가 0이어도 UPDATE는 행을 찾아 락을 건 뒤 WHERE를 평가함)

## 검증
atomic-high-r1 구간 Prometheus 지표:

| 지표 | 값 |
|---|---|
| Hikari active 최대 | 10 (풀 전부 사용) |
| Hikari pending 최대 | 190 |
| 커넥션을 얻기까지 걸린 시간 최대 | 0.402초 |
| Tomcat 사용 중 스레드 최대 | 200 (전부) |
| 커넥션 1회 사용 시간 평균 | 3.5ms |

- `docker stats` 기준 MySQL CPU는 3,000 구간에서 약 60% (CPU 2개 제한이라 최대 200%). **가설 2는 아님**
- 가설 1이 맞음: 커넥션 10개가 꽉 차고 190개 요청이 줄을 섬. 조회도 같은 줄에 섬
- 가설 3은 아직 검증 안 함. 커넥션 1회 사용 3.5ms가 왕복 3번치고 길어서 행 락 대기가 섞였을 가능성이 있음
