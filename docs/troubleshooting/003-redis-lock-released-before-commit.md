# 003. 분산 락을 걸었는데 300명이 샀다: 락이 커밋보다 먼저 풀림

- 단계: step03 / 날짜: 2026-10-26
- 원본 결과: `k6/results/step01-spike-step03-*`, `k6/results/step03-mixed-*`
- 태그: `step-03-broken` (트랜잭션 안에서 락 해제) → `step-03-fixed`

## 배경
02단계에서 원자적 UPDATE를 골랐지만, 재고 규칙이 WHERE 한 줄로 안 되면 비관적 락이 필요하다. 그런데 비관적 락은 기다리는 동안에도 DB 커넥션을 쥐고 있다. 대기를 DB가 아니라 Redis에서 하게 하면 어떨까 싶어서 Redis 분산 락을 붙였다. 재고 계산은 02단계 이전처럼 엔티티에서 한다(읽기-계산-쓰기).

## 현상
`ProductService.decreaseStock` 안에서 락을 잡고 `finally`로 풀었다.

```java
@Transactional
public Product decreaseStock(Long productId, int quantity) {
    return redisLock.executeWithLock("lock:product:" + productId, () -> {
        Product product = getProduct(productId);
        product.decreaseStock(quantity);
        return product;
    });
}
```

- `OrderConcurrencyTest`(재고 50, 100스레드): `expected: 50 but was: 100`
- 스파이크(재고 100, 300명):

| 회차 | 성공 | 품절 | 남은 재고 | 초과 판매(diff) | p95 |
|---|---|---|---|---|---|
| 1 | 248 | 52 | 0 | 148 | 1.35초 |
| 2 | 299 | 1 | 0 | 199 | 1.03초 |
| 3 | 300 | 0 | 23 | 223 | 0.91초 |

- 락은 900번(회차당 300번) 정상적으로 잡히고 풀렸다. 락이 고장 난 게 아니라 락이 지키는 범위가 틀렸다.

## 가설
1. 더티 체킹 때문에 `UPDATE`가 커밋 시점에 나간다. 락 안에서는 `SELECT`만 실행되고, 쓰기는 락이 풀린 뒤에 일어난다.
2. `UPDATE`를 락 안에서 내보내도 **커밋**은 락이 풀린 뒤에 일어난다. 다음 요청은 커밋되지 않은 변경을 못 보므로 예전 값을 읽는다.

## 검증
순진한 버전의 한 요청을 시간순으로 적으면:

```
[tx1 시작: 커넥션 빌림] → 락 획득 → SELECT stock(100) → 엔티티 stock=99 (메모리만)
→ 락 해제 → INSERT orders → [커밋: UPDATE product SET stock=99]
```

가설 1만 원인이라면 `saveAndFlush`로 락 안에서 UPDATE를 내보내면 고쳐져야 한다. → 아래 "실패한 시도"에서 확인했고 고쳐지지 않았다. 가설 2가 원인이다.

## 실패한 시도
- **`saveAndFlush`로 UPDATE를 락 안에서 실행**: 테스트 96/50 성공, 스파이크 197개와 179개 판매(재고 100). 줄었을 뿐 그대로다.
  - 다음 요청이 락을 얻고 SELECT하면 앞 요청이 아직 커밋 전이라 예전 값(100)이 보인다.
  - 그 요청의 UPDATE는 앞 요청이 쥔 행 X락 때문에 커밋까지 기다렸다가, 예전 값으로 계산한 99를 덮어쓴다.

## 해결
락이 트랜잭션 전체를 감싸게 옮겼다: **락 획득 → 트랜잭션 시작 → 커밋 → 락 해제.** 결제 실패 보상(재고 복구) 트랜잭션도 같은 락으로 감쌌다.

```java
Order order = redisLock.executeWithLock(lockKey, () -> transactionTemplate.execute(status -> {
    Product product = productService.decreaseStock(productId, quantity);
    return orderRepository.save(Order.create(userId, productId, quantity, product.getPrice()));
}));
```

| 선택지 | 판단 |
|---|---|
| 락으로 트랜잭션 전체를 감쌈 (채택) | 커밋이 끝난 뒤 락이 풀린다. 락을 트랜잭션 밖에서 기다리므로 대기 중에는 DB 커넥션을 쥐지 않는다 |
| 커밋 후 콜백(`TransactionSynchronization.afterCompletion`)에서 해제 | 커밋 뒤에 풀리긴 하지만, 락을 트랜잭션 안에서 잡으므로 기다리는 동안 커넥션을 쥔다 |
| Redisson으로 교체 | 락 구현이 좋아질 뿐 락을 어디에 두느냐는 그대로다. 같은 버그가 난다 |

## 결과

### 1) 정합성: 스파이크 (재고 100, 300명), 방식마다 3회

Redis 컨테이너를 띄운 환경에서 비관적 락과 원자적 UPDATE도 다시 측정했다.

| 방식 | 성공 / 품절 | 남은 재고 | p95 (3회) |
|---|---|---|---|
| Redis 락 (순진한 위치) | 248~300 / 0~52 | 0~23 ❌ | 0.91~1.35초 |
| Redis 락 (트랜잭션 감쌈) | 100 / 200 | 0 ✅ | 0.87~1.75초 |
| 비관적 락 | 100 / 200 | 0 ✅ | 0.52~0.68초 |
| 원자적 UPDATE | 100 / 200 | 0 ✅ | 0.45~0.71초 |

- 세 방식 모두 1회차가 가장 느리다(JVM 워밍업).
- Redis 락이 가장 느리다. 품절 응답 200건도 전부 락 줄을 서고, 락이 풀린 뒤 대기자가 깨어나기까지 최대 10ms(스핀 간격)의 빈 시간이 생기기 때문이라고 추정한다.

### 2) 인기 상품 주문 + 다른 상품 조회 (PG 지연 0)

`k6/scripts/step03-mixed.js`: 인기 상품(2번) 주문을 300 → 600 → 900 RPS로 올리면서, 상관없는 상품 조회(`GET /api/products/1`)를 초당 50건 함께 보낸다. 앱은 `--pg.latency-ms=0`.

**가설**: 비관적 락과 원자적 UPDATE는 DB 안에서 행 락을 기다리며 커넥션을 쥔다. 대기자가 커넥션 10개를 다 차지하면 조회도 커넥션을 기다린다. Redis 락은 DB 밖에서 기다리므로 조회는 덜 느려질 것이다.

단계별 수치 (2회차, 각 단계 끝 40초 구간, 서버 처리량은 Prometheus):

| 방식 | 단계 | 주문 처리(TPS) | Tomcat busy 최대 | Hikari pending 최대 | 조회 p95 (K6) |
|---|---|---|---|---|---|
| Redis 락 | 300 | 300 | 69 | 0 | 10ms |
| | 600 | **약 310** | **200** | 0 | **4.5초** |
| | 900 | 약 400 | 200 | 0 | 4.5초 |
| 비관적 락 | 300 | 300 | 1 | 0 | 10ms |
| | 600 | 600 | 43 | 33 | 10ms |
| | 900 | 약 840 | 200 | 190 | 1.7초 |
| 원자적 UPDATE | 300 | 300 | 3 | 0 | 10ms |
| | 600 | 600 | 33 | 24 | 10ms 미만 |
| | 900 | 약 760 | 200 | 190 | 1.8초 |

전체 요약 (1회차 / 2회차):

| 방식 | 주문 성공 | 주문 p95 | 조회 p95 | Hikari pending 최대 | SET NX 시도 |
|---|---|---|---|---|---|
| Redis 락 | 53,477 / 60,701 (실패 66 / 17건, 락 대기 5초 초과 503) | 6.47 / 5.28초 | 5.25 / 4.40초 | 0 / 0 | 약 214만 / 211만 회 |
| 비관적 락 | 90,344 / 99,202 | 2.88 / 1.79초 | 2.76 / 1.69초 | 190 / 190 | — |
| 원자적 UPDATE | 90,702 / 98,328 | 2.55 / 1.89초 | 2.35 / 1.77초 | 190 / 190 | — |

- **커넥션에 대한 예측은 맞았다.** Redis 락은 Hikari pending 0, active 최대 3이었다.
- **결론은 틀렸다.** Redis 락은 주문 처리량이 약 300~400 TPS에서 막혔고, 그 순간 Tomcat 스레드 200개가 전부 락을 기다리며 스핀했다. 조회 요청은 커넥션이 아니라 **스레드**를 못 받아서 4.5초를 기다렸다. 비관적 락과 원자적 UPDATE는 600 구간까지 조회 p95 10ms였다.
- 대기 장소가 커넥션 풀에서 Tomcat 스레드로 옮겨졌을 뿐이다. 둘 다 모든 요청이 같이 쓰는 자원이라, 줄이 넘치면 상관없는 요청도 막힌다.
- 900 구간의 비관적 락 vs 원자적 UPDATE 차이(840 vs 760)는 1회차(약 560 vs 680)와 뒤집혀 있다. 02단계와 마찬가지로 이 맥의 한계 구간이라 결론을 내리지 않는다.

**Redis 락의 처리량이 절반인 이유 (추정)**
- 주문 하나가 락을 쥐는 동안 하는 일: `SET NX` 왕복 → 커넥션 빌림, 트랜잭션 시작 → SELECT, INSERT, UPDATE, 커밋 → 커넥션 반납 → Lua 해제 왕복.
- 커넥션 점유 시간은 평균 약 1.7ms인데, 300 TPS면 락 한 번에 약 3.3ms다. 나머지 약 1.6ms는 Redis 왕복과 트랜잭션 준비 같은 DB 밖 작업이다. 이 시간에도 다른 요청은 아무도 재고를 만질 수 없다.
- 비관적 락은 행이 잠기는 구간이 `SELECT ... FOR UPDATE`부터 커밋까지뿐이다. 다음 대기자는 이미 커넥션을 쥐고 트랜잭션을 연 채 DB 안에서 기다리므로, 락이 풀리면 바로 이어 받는다.
- 스핀 대기도 비용이다. 대기자 200명이 10ms마다 `SET NX`를 보내서 Redis에 초당 약 1만 8천 번 요청이 갔다. 락을 얻은 건 그중 초당 300~400번이다.

### 최종 선택
- 정합성 버그(락 해제가 커밋보다 먼저)는 락이 트랜잭션을 감싸게 해서 고쳤다 → `step-03-fixed`
- 하지만 **이 프로젝트의 재고 차감에는 Redis 락을 쓰지 않는다.** 재고 규칙이 WHERE 한 줄로 되는 지금은 원자적 UPDATE가 처리량(약 2배), 다른 요청 지연, 코드 단순함에서 모두 낫다.
- Redis 락이 의미 있는 곳: 지키려는 것이 DB 행 하나가 아닐 때 (외부 API 호출, 여러 저장소에 걸친 작업, 배치 중복 실행 방지). 또는 대기를 하지 않고 바로 실패시키는 용도 (tryLock, 대기 0).

## 배운 것
- 락은 "무엇을" 지키는지보다 "어디서 풀리는지"가 중요하다. 트랜잭션 안에서 풀린 락은 커밋 전 데이터를 남에게 넘겨준다.
- 더티 체킹을 쓰면 SQL이 나가는 시점이 코드 순서와 다르다.
- "커넥션을 안 쥔다"는 장점은 실제였지만, 대기자가 스레드를 쥐고 있으니 줄이 서는 장소만 바뀌었다. 대기 자체를 없애거나(바로 실패) 대기자 수를 제한해야 다른 요청이 보호된다.
- 분산 락은 락을 쥐는 구간에 Redis 왕복이 두 번 더 들어간다. 한 행에 몰리는 경합에서는 그 몇 ms가 처리량 상한을 정한다.
