# 002. 빨라졌는데 여전히 300명이 샀다: 갱신 손실과 세 가지 해법

- 단계: step02 / 날짜: 2026-10-22
- 원본 결과: `k6/results/step01-spike-step02-*`, `k6/results/step02-hot-*`
- 태그: `step-02-broken` → 비관적 락, 낙관적 락, 원자적 UPDATE 커밋 (각 방식은 커밋 단위로 측정)

## 현상
01단계에서 PG 호출을 트랜잭션 밖으로 뺀 코드(step-01-fixed)로 스파이크 테스트(재고 100개, 300명 동시 1회 주문)를 3번 돌렸다.

| 회차 | 주문 성공 | 품절(409) | 남은 재고 | p95 |
|---|---|---|---|---|
| 01단계 기준(트랜잭션 분리 전) | 300 | 0 | 70 | 9.26초 |
| 1 | 300 | 0 | 64 | 1.08초 |
| 2 | 300 | 0 | 65 | 871ms |
| 3 | 300 | 0 | 65 | 764ms |

- 응답은 약 10배 빨라졌지만 정합성은 그대로다. 에러도 0건이다.
- 테스트 코드(`OrderConcurrencyTest`, 재고 50개에 100스레드)도 `expected: 50 but was: 100`으로 실패했다.

## 가설
1. 재고 차감이 읽기-계산-쓰기(read-modify-write)라서, 동시에 읽은 트랜잭션들이 서로의 변경을 덮어쓴다 (갱신 손실)
2. 트랜잭션이 짧아졌으니 충돌 확률은 줄었겠지만, 락이 없으니 0이 될 수는 없다

## 검증
- 300 ÷ 35(실제로 줄어든 재고) ≈ 8.6. 커넥션이 10개라 동시에 최대 10개 트랜잭션이 같은 재고를 읽고, 그중 하나의 쓰기만 남는 모양과 맞다.
- Hibernate는 커밋 시점에 `UPDATE product SET stock = 99 ...`처럼 **계산된 값**을 쓴다. DB 입장에서는 "99로 바꿔라"라는 요청이 여러 번 온 것일 뿐이라 막을 이유가 없다.
- MySQL 기본 격리 수준(REPEATABLE READ)의 일반 SELECT는 락 없는 스냅샷 읽기라서, 남이 같은 행을 읽고 고치는 것을 막지 않는다.

## 해결 후보 비교
세 방식을 각각 커밋하고, 같은 테스트로 측정했다. 결제 실패 시 재고 복구(보상)도 각 방식과 같은 방법으로 바꿨다. 차감만 고치고 복구를 그대로 두면 복구에서 갱신 손실이 생긴다.

| 방식 | 구현 | 충돌 시 |
|---|---|---|
| 비관적 락 | `@Lock(PESSIMISTIC_WRITE)` → `SELECT ... FOR UPDATE` | 커밋될 때까지 기다린다 |
| 낙관적 락 | `@Version` → `UPDATE ... WHERE id = ? AND version = ?`, 최대 30회 재시도(5~30ms 지터) | 실패하고 트랜잭션을 통째로 다시 실행한다 |
| 원자적 UPDATE | `UPDATE product SET stock = stock - ? WHERE id = ? AND stock >= ?` | DB가 행 X락을 잡고 최신 값으로 계산한다. 0행이면 품절 |

## 결과

### 1) 정합성: 스파이크 (재고 100, 300명), 방식마다 3회

| 방식 | 성공 / 품절 | 남은 재고 | p95 (3회) | 비고 |
|---|---|---|---|---|
| 락 없음 | 300 / 0 | 64~65 ❌ | 0.76~1.08초 | |
| 비관적 락 | 100 / 200 | 0 ✅ | 0.55~0.75초 | |
| 낙관적 락 | 100 / 200 | 0 ✅ | 0.78~1.18초 | 재시도 677 / 799 / 809회 |
| 원자적 UPDATE | 100 / 200 | 0 ✅ | 0.49~0.76초 | |

### 2) 성능: 인기 상품 하나에 100 → 200 → 300 RPS (PG 300ms)

| 방식 | p95 | 처리 건수 | 실패 | 판매 기록 손실(diff) |
|---|---|---|---|---|
| 락 없음 | 315ms | 33,749 | 0 | **1,105** ❌ |
| 비관적 락 | 312ms | 33,749 | 0 | 0 |
| 낙관적 락 | **12.27초** | 24,585 | **292** (재시도 30회 소진) | 0 |
| 원자적 UPDATE | 311ms | 33,749 | 0 | 0 |

- 낙관적 락은 200 RPS까지 버티다가 300 RPS에서 처리량이 **약 135 TPS로 오히려 떨어졌다.** 재시도 86,852회, dropped_iterations 8,872.
- 비관적 락이 락 없을 때와 차이가 없는 이유: PG 호출이 트랜잭션 밖에 있어서 락을 쥐는 시간이 수 ms뿐이다. (01단계 해결이 02단계 락 비용을 낮춰 준 셈)

### 3) 한계: PG 지연 0, 400 → 800 → 1,200 RPS (DB 락만 보이게)

서버가 처리한 초당 건수(Prometheus, 15초 간격):

| 방식 | 400 구간 | 800 구간 | 1,200 구간 | 실패 | 손실 |
|---|---|---|---|---|---|
| 락 없음 | 400 | 800 | 약 910 | 0 | **53,812** ❌ |
| 비관적 락 | 400 | 800 | 830 → 약 520 | 0 | 0 |
| 원자적 UPDATE | 400 | 800 | 850 → 약 710 | 0 | 0 |
| 낙관적 락 | 400 | **약 250** | 약 245 | 1,000 | 0 |

- 800 RPS까지는 비관적 락과 원자적 UPDATE 모두 락 없을 때와 같다.
- 낙관적 락은 800 RPS 구간에서 재시도 폭풍으로 붕괴했다 (재시도 244,076회).
- 낙관적 락 붕괴 구간에서 Hikari pending이 최대 약 160까지 올랐다. 재시도마다 커넥션을 다시 빌리기 때문에, 결국 01단계의 커넥션 고갈로 되돌아간다.
- **1,200 구간의 비관적 락 vs 원자적 UPDATE는 결론을 내리지 않는다.** 두 방식만 다시 돌렸더니 순위가 뒤집혔다.

| 방식 | 1회차 1,200 구간 | 2회차 1,200 구간 |
|---|---|---|
| 비관적 락 | 830 → 약 520 (p95 3.08초) | 약 830 유지 (p95 1.97초) |
| 원자적 UPDATE | 850 → 약 710 (p95 2.11초) | 820 → 약 430 (p95 3.47초) |

  이 맥에서 락 없이도 약 910이 한계인 구간이라, 앱과 K6와 MySQL이 CPU를 나눠 쓰는 노이즈가 방식 차이보다 크다.

## 실패한 시도
- **트랜잭션을 줄이면 동시성도 나아질 것이라는 기대**: 응답은 10배 빨라졌지만 초과 판매는 그대로였다. 짧아진 트랜잭션도 커넥션 10개가 동시에 같은 행을 읽기에는 충분히 길다.
- **낙관적 락 + 재시도**: 정합성은 맞췄지만 한 행에 요청이 몰리는 타임딜에서는 재시도가 재시도를 불러 처리량이 무너졌다. 재시도 횟수를 늘리면 실패는 줄겠지만 지연과 DB 부하는 더 커진다.

## 해결
**원자적 UPDATE**를 채택했다.
- 낙관적 락: 한 행에 요청이 몰리는 타임딜에서 재시도 폭풍으로 처리량이 무너져서 제외
- 비관적 락: 성능은 원자적 UPDATE와 차이가 없었다. 재고 규칙이 복잡해지면(조건이 여러 행, 여러 필드에 걸치면) 다시 고려한다
- 원자적 UPDATE: 재시도와 락 관리 없이 쿼리 하나로 끝난다. 대가로 재고 규칙("남은 개수 ≥ 주문 개수")이 엔티티가 아니라 SQL에 있다
- 낙관적 락용 `version` 컬럼은 V3 마이그레이션으로 지웠다

## 배운 것
- "빨라졌다"와 "맞다"는 다른 문제다. 성능을 고쳐도 동시성은 저절로 고쳐지지 않는다.
- 락의 비용은 락을 쥐는 시간이 정한다. 트랜잭션 안에 느린 작업이 없으면 비관적 락도 싸다.
- 낙관적 락은 "충돌이 드물다"는 전제 위에서만 가볍다. 타임딜은 그 전제의 정반대다.
- 보상(재고 복구)도 차감과 같은 동시성 제어를 써야 한다.
