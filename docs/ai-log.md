# AI 활용 기록

> Claude의 실수, 사용자의 수정, 효과가 좋았던 프롬프트를 숨기지 않고 기록한다. (CLAUDE.md 9.2)

## 2026-10-21 / 준비 — AI와 함께 작업 규칙(CLAUDE.md)부터 설계
- 상황: 코드를 쓰기 전에, AI가 이 프로젝트에서 어떻게 일해야 하는지부터 정하기로 함
- AI 제안: 협업 규칙(변경 전후 설명, 이해 확인 질문), "일부러 터뜨리고 고친다" 진행 방식, 단계별 기록 규칙, 로드맵을 CLAUDE.md에 고정하자고 제안함. 도메인은 동시성, 멱등성, 사가, 아웃박스가 억지 없이 다 들어가는 타임딜 주문으로 추천함
- 실제 결과: 대부분 채택함. 이해 확인 질문은 AI가 처음에 제안한 "답해야만 진행"이 아니라 "질문만 던지고 진행"으로 바꿈
- 사람이 판단한 것: 스택(Spring Boot 3 + Java 21), 모놀리스로 시작해서 나중에 분리, 티스토리 일기 형식 → AI가 혼합형(TL;DR + 일기 본문 + 정리)을 제안했고 받아들임
- 글에 쓸 포인트: "AI에게 코드를 시키기 전에 일하는 방식부터 정했다". CLAUDE.md는 지침일 뿐 강제되지 않는다는 한계도 같이 쓸 것 (반복해서 어기면 hook으로 강제할 예정)

## 2026-10-21 / step00 — AI의 00단계 설계에 PK와 인덱스 결정이 빠져 있었음
- 상황: AI가 00단계 설계(엔티티, API, 흐름, 의존성)를 제시함
- AI 제안: 엔티티 필드만 나열했고, PK 생성 전략과 인덱스 설계는 언급하지 않음
- 실제 결과: 사용자가 "PK는 뭘로 잡을지, 단일 인덱스와 복합 인덱스 중 무엇을 쓸지도 정해야 한다"고 지적함 → 설계를 보완함
- 사람이 판단한 것: 스키마 설계(PK, 인덱스)를 기능 설계와 같은 무게로 다뤄야 한다는 점. 인덱스와 PK가 성능에 미치는 영향을 연재에서 보여주기로 함
- 글에 쓸 포인트: AI는 "동작하는 설계"를 빨리 내놓지만 데이터 볼륨과 운영 관점은 빠뜨리기 쉽다. 체크리스트는 사람이 들고 있어야 한다

## 2026-10-21 / 계획 — 로드맵 수정: 인덱스와 PK 단계 추가, 부하 테스트 중심으로 전환
- 상황: 사용자의 PK와 인덱스 지적을 반영하고, "프로젝트 생성은 짧게, 부하 테스트로 문제를 하나씩 찾아 고치는 모습을 보여달라"는 요청을 받음
- AI 제안: 02단계에 "데이터 볼륨, 인덱스, PK 전략"을 끼워 넣고 이후 단계 번호를 하나씩 미룸
- 사람이 판단한 것: 연재의 무게중심을 부하 테스트 주도의 문제 발견으로 옮김
- 글에 쓸 포인트: 계획은 AI가 짰지만 방향을 바꾼 건 사람이다

## 2026-10-21 / step00 — Spring Boot 3.x가 Initializr에서 사라져 있었음
- 상황: Boot 3 + Java 21로 프로젝트를 생성하려 함
- AI 제안: 처음엔 Initializr에서 바로 생성하려 했으나, 확인해 보니 선택지가 4.x뿐이었음(기본값 4.1.1). Maven Central에서 3.x 최신 버전(3.5.16)을 확인한 뒤, 3.5.16으로 갈지 4.1.1로 갈지 사용자에게 물어봄
- 사람이 판단한 것: 국내 실무 기준에 맞춰 3.5.16을 선택함 (오픈소스 지원 종료는 인지하고 감수함)
- 글에 쓸 포인트: AI가 "Boot 3"라는 전제를 그대로 받지 않고 실제 생태계 상태를 확인함. 버전 선택이 기술 문제가 아니라 맥락(채용 시장)에 따른 결정이었다는 점

## 2026-10-21 / step01 — 관측 환경 구성, GitHub 공개 저장소 생성
- 상황: K6보다 먼저 Prometheus와 Grafana를 붙이고, 비밀값을 ignore 처리한 뒤 GitHub에 올리기로 함. 사용자는 Claude in Chrome으로 진행해 달라고 요청함
- AI 제안: gh CLI가 이미 로그인돼 있는 걸 확인하고, 브라우저 자동화보다 CLI가 빠르고 재현 가능하다고 제안함 → 사용자가 수락함. 커뮤니티 대시보드를 가져오는 대신, 부하 테스트에서 실제로 볼 지표(RPS, p95/p99, Hikari active/pending/획득 시간/점유 시간, Tomcat 스레드, JVM)만 담은 대시보드를 코드로 작성함. push 전에 gitleaks로 git 이력 전체를 검사하는 `make secret-scan`을 추가함
- 실제 결과: 모두 동작함. AI가 쓴 검증 명령 하나가 zsh 글로빙(`?`를 패턴으로 해석) 때문에 실패해서 URL을 따옴표로 감싸 다시 실행함
- 사람이 판단한 것: 저장소 이름과 공개 범위, 생성 방법
- 글에 쓸 포인트: "로그인돼 있으니 브라우저로 해달라"는 요청에 AI가 더 단순한 도구를 제안한 사례. 지표 없이 부하 테스트를 하면 원인을 추측할 수밖에 없다는 점

## 2026-10-21 / step01 — AI의 사전 가설이 틀림: "30초 뒤 타임아웃 에러 폭증"은 일어나지 않았음
- 상황: 첫 load 테스트 전에 AI가 결과를 예측함
- AI 제안: "40 RPS 이상에서 Hikari 대기가 쌓이고, 30초(connectionTimeout) 뒤 SQLTransientConnectionException이 쏟아질 것"
- 실제 결과: 에러 0%, p95 38초. Hikari 대기는 최대 12초였고 타임아웃은 0건. Tomcat 스레드(200개)가 Hikari 대기열의 길이를 제한해서, 나머지 대기는 서버 지표에 잡히지 않는 Tomcat 앞단에서 일어났음. AI는 이 상호작용을 놓쳤음
- 사람이 판단한 것: (사용자에게 공유 예정) 해결 방향 선택
- 글에 쓸 포인트: 가설을 먼저 적어 두고 데이터로 틀렸음을 확인하는 과정 자체가 트러블슈팅. AI의 예측도 검증 대상이다. 또 대시보드를 미리 만들어 둔 덕분에 서버와 클라이언트 지표의 29초 차이를 발견할 수 있었음
